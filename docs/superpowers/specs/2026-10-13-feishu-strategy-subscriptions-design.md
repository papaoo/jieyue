# 阶跃：飞书多策略订阅与研究雷达设计

日期：2026-10-13；2026-10-15 状态：数据验收核心、只计算适配器、多群管理 API/UI、14 类独立绑定、历史研究/有界 AI 解释和单群固定测试已实现。正式发布、自动调度和四类非股票内容生产者尚未接通。总路线见 [开发规划](../plans/2026-10-13-feishu-push-roadmap.md)，实际边界以 [开发验收说明](../../feishu-research-delivery.md) 为准；下文其余部分保留原始设计，不作为全部完成声明。

适用范围：用户本人及熟悉的研究伙伴内部试用。提供可追溯的筛选结果、事件事实和研究解释，不接券商下单，不承诺收益。当前在本地分批实现与离线验收；不建群、不保存真实凭据、不发消息、不启用定时任务、不修改服务器、不提交 Git。

## 1. 决策摘要

- 保留“一策略一群”：10 个现有股票筛选策略群、1 个 ETF 轮动群、2 个资讯群、1 个管理员状态群，共 14 个正式群；另建 1 个联调测试群。
- V1 使用每群独立的飞书自定义机器人 Webhook。共用采集与计算，按订阅分发，不为每个群重复抓全市场。
- 新订阅默认“确定性规则排序 + LLM 解释最终结果”；AI 重排作为显式可选模式，不改变现有手动选股默认行为。
- 股票策略先做收盘后日报；盘中雷达先观察、不默认群发。正式发布同时依赖时间窗口、数据验收、内容审核及目标群开关。
- 首次上线和规则变更后人工审核；稳定后由管理员逐订阅开启自动放行。建群、配置机器人、开启推送是三个不同动作。

### 方案取舍

| 方案 | 优点 | 代价与边界 | 选择 |
| --- | --- | --- | --- |
| 每群一个 Webhook | 配置简单；无需接收群消息；适合定时卡片 | 每群维护凭据；不做群内命令；超时送达状态可能未知 | V1 推荐 |
| 飞书应用机器人 | 可扩展群内查询、订阅操作及应用级权限 | 应用权限、事件接收、身份和指令授权更复杂 | V2 按需接入 |
| 现有全局通知直接广播 | 改动少 | 无法可靠绑定不同策略、参数和群；容易重复或误发 | 不采用 |

群名可以改，后台必须绑定稳定策略 ID，不用中文名称判断路由。V1 股票策略范围为 A 股；不把同一套阈值直接用于 BTC、黄金、美股。

命名边界必须写进群公告：双低不是可转债双低；资金热度不代表真实主力净流入；蓝筹收益质量没有强制连续分红或高股息条件；“质量”名称不等于已验证完整 ROE/现金流质量；超跌候选不等于底部已确认。策略分数不是盈利概率。

### 建群与机器人配置步骤

1. 先建 T00，再创建上表正式群。研究群仅邀请内部伙伴；O01 只邀请管理员。
2. 每个群进入“群设置 → 群机器人 → 添加机器人 → 自定义机器人”，名称统一为“阶跃研究助手”。每群独立创建，不复用其他群的 Webhook。[飞书官方指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)
3. 开启签名校验，单独保存该群 Webhook 和签名密钥；如果再设置关键词，统一为“阶跃”，发送器须保证每种消息都包含该关键词。先不要配置未经核实的 IP 白名单，服务器代理出口不一定等于服务器公网 IP。
4. 将凭据放密码管理器或受保护的私密配置中，按 S01 等编号标记。不要发到聊天、群公告、普通共享表格或 Git 仓库。群主可按飞书支持的选项限制机器人编辑/移除权限。
5. 在“设置 → 通知渠道 → 多群研究推送”逐群录入并绑定分类；新目标默认暂停。旧 `FEISHU_WEBHOOK_URL` 仍是单目标，不能用逗号拼接多个 URL，也不会被新的群路由复用。
6. 先在 T00 预览并明确确认一条测试；正式群也逐个确认目标。以后任何真实测试按钮都属于外发动作，不能由“保存配置”隐式触发。

Webhook 模式不需要先填写 App ID、App Secret、Chat ID 或配置事件回调。若组织策略禁止添加自定义机器人，需要联系该组织管理员；不能通过其他群凭据绕过。

可反馈的非敏感清单：`群编号 / 群名 / 已建群 / 已建机器人 / 已开启签名 / 关键词 / 是否完成目标确认`。不需要把 Webhook 或密钥发给助手。

群公告模板：

> 阶跃内部研究试用。本群发布【策略名称】规则筛选结果及证据解释，不执行交易。请先查看数据日期、覆盖范围和风险提示；排名不等于收益保证。数据不完整时会标记延期或降级，不用过期结果冒充当日结论。

## 4. 数据需要补什么

目标是补齐“可用性与证据链”，不先采购一堆接口。以下频率是本系统建议抓取计划，不是供应商实时性保证。

| 数据层 | 用途与最低要求 | 采集建议 | 权限/成本处理 |
| --- | --- | --- | --- |
| 交易日历、股票列表、ST/停复牌 | 确定预期股票池与有效交易日 | 每日 08:10 更新；盘后复核 | 优先复用已接入源；权限逐接口实测 |
| A 股日线、复权因子 | 技术指标与跨日比较 | 盘后按日期批量增量；首次补足有效历史 | Tushare 为优先候选，现有其他源作经口径验证的备用 |
| PE/PB、市值、换手、量比 | 价值、流动性和活跃度规则 | 同交易日 `daily_basic` 批量拉取 | 官方要求至少 2000 积分；有额度边界，不等于全部接口无限量 |
| 指数及市场宽度 | 雷达与市场风险背景 | 早报用上个完整交易日，晚报用当日验收批次 | 标记统计股票池、来源、业务日期；缺数不能记零 |
| 行业/概念成分与涨跌 | 板块解释、共振 | 盘后更新；盘中仅在授权源稳定时启用 | 免费源存在稳定性/时效边界；概念缺失不编造榜单 |
| ETF 全资产池与防守资产 | 轮动信号、风险比较 | 盘后统一复权日线，末日必须对齐 | 逐资产核验；权限不足不能静默把防守 ETF 替换为现金 |
| 新闻与公司公告 | 候选风险、催化事件 | 07:00—22:00 每 15 分钟增量扫描；20:30、22:00 补查 | 优先合法可用的公开来源/已有检索额度；不承诺秒级快讯 |
| 财务、分红、股东、解禁/回购 | 提升价值和事件研究质量 | 按披露增量，每晚校验，不必每分钟拉 | 复用现有适配，逐接口探测；缺权限显示原因 |
| 资金流、龙虎榜、筹码 | 增强解释，部分未来策略所需 | 盘后或供应商更新后 | 非本期全部策略必需；筹码等缺权限先不展示，不让 LLM 估造 |
| 盘中分钟数据 | 未来盘中策略/预警 | 可选交易时段每 5 分钟 | 先核验独立权限、延迟与配额，不以 2000 积分推定已包含 |

Tushare 官方日线一般在交易日 15:00—16:00 更新；`daily_basic` 为 15:00—17:00。因此本方案选择 17 点以后发布正式规则榜，而不是 15:01 就把尚未齐备的数据当作收盘结果。实际完成情况仍须验收。[日线文档](https://tushare.pro/document/2?doc_id=27)、[每日指标文档](https://tushare.pro/document/2?doc_id=32)

当前用户提供的“2000 积分 + 已有模型 Key + 免费源”可作为第一期验证起点，不等于本方案所有增强项已具备权限。本轮不消费这些 Key。开发时先生成“接口—权限—最后成功日期—覆盖率—配额错误”矩阵，再列出确实阻断目标功能的付费项，由用户决定是否开通。公共可读不代表允许全文再分发；内部群以事实摘要、短摘录和原文链接为主，商业化前另核验数据与内容许可。

### 策略数据依赖与数据验收

- 放量突破、缩量回踩、低波质量必须有对应日线技术指标；其余策略按 YAML 实际规则声明快照、估值等必需字段。不能关闭日线补数后跳过硬条件。
- 初次历史预热以“有效交易日 K 线数量 + 指标预热期”验收，不把 120 个自然日等同 120 根有效日线。ETF 按配置窗口及所展示统计的历史长度单独验收。
- 现有技术补数存在前 100 个候选上限。V1 显式记录“股票池总数 → 快照初筛数 → 送入技术验证数 → 成功数 → 入选数”；若仍采用这个上限，卡片称为“初筛候选池排名”，不能称“全市场技术排名”。扩大范围需先分批预热和压测，不直接无限并发。
- “声明范围”分层冻结：快照验收覆盖订阅股票池；技术验收覆盖按已声明规则选出的前 N 初筛池。未进入前 N 的股票标记“未做技术评估”，不能记作“不满足技术条件”；进入前 N 后补数失败，也不能通过临时缩小 N 隐藏缺失。
- 日终正式批次要求声明范围内必需数据均有有效状态：有效值、已确认业务不适用或已确认不满足条件。无法解释的必需缺失产生部分结果草稿并阻断正式榜；不自动缩小股票池。停牌、亏损 PE 不适用、新股历史不足须分别记录，不能都算采集失败或填零。
- 核心快照过期、股票池基准不明、字段单位/复权冲突，整份阻断；个股缺数先补采并披露剔除范围，正式发布仍受前述覆盖门禁约束。可选新闻缺失则允许规则榜，标明“事件信息未核实”。
- ETF 要求风险资产及配置防守资产最新有效日期一致；某资产末日缺价不得自动换现金后仍冠以原配置的正式结果。
- 缓存键包含业务日期、股票代码、频率、复权口径、来源及版本；不能只依赖 24 小时 TTL。不同来源字段只有定义、单位和日期一致时才合并，冲突保留审计。

## 5. 采集、计算、发布时间表

统一时区 `Asia/Shanghai`，A 股按交易日历运行；节假日不能只用周一至周五判断。新闻可在非交易日继续采集，策略不伪造新交易日结果。

| 时间/条件 | 动作 | 对群的影响 |
| --- | --- | --- |
| 08:10 | 更新交易日历、基础股票池；核对隔夜事件 | 不直接推股票榜 |
| 08:40 | R01 早报 | 明确 A 股行情截至上个完整交易日；新事件标发布时间 |
| 交易时段，可选 | 每 5 分钟采集授权行情；更新内部观察缓存 | V1 默认不发盘中策略榜；启用须单独验收 |
| 07:00—22:00，每 15 分钟 | 公告/新闻索引增量抓取、去重、主体匹配 | R02 仅新出现且达到重要性门槛时发 |
| 15:30、16:00、16:30、17:00 | 日线、每日指标、ETF 增量补齐和验收 | 数据准备阶段，不强制发布 |
| 17:05 起 | 固化合格数据批次，排队跑策略 | 各策略计算共用快照与历史缓存 |
| 17:10—17:55 | 按第 2 节窗口逐策略释放 | 时间到但未准备好则等待，不使用旧日期冒充 |
| 18:00 起 | ETF 观察卡；调仓日另标正式信号 | 默认周频；周/月最后交易日，而非固定星期五 |
| 18:10 起 | R01 晚报 | 汇总已完成批次；未完成策略明确列“待完成” |
| 17:10—19:00 | 尚缺的数据最多每 10 分钟有界重试 | 明确无权限的接口停止反复重试，通知 O01 |
| 19:00 截止 | 当日收盘报告停止继续发布，未完成任务过期 | 相关群一次“延期/未完成”状态；O01 给原因；不深夜补发旧榜 |
| 20:30、22:00 | 财务/公告补查 | 重大新增事件进入 R02；不悄悄改写已发策略报告 |

ETF 必须保留现有策略的执行假设：周/月最后交易日收盘计算、下一交易日收盘执行假设；本系统不下单。每日观察卡不是每天调仓。不同市场 ETF 的价格与节假日情况按实际配置验证。

截止规则贯穿投递：S01—S11 日终报告及 R01 晚报的 outbox 保存当日 `not_after=19:00`，首次发送、重试和下一分片之前都检查；`ready/pending/retry_wait` 也不能越过截止。已经成功的分片保留，不整体重发。R01 早报截止 09:15；R02 当日发布窗口截止 22:00，窗口外事件进入下一窗口并注明原始时间。迟到批准不能复活过期任务；管理员需要越过截止时，必须单独批准“历史补发”新 revision 并显示原交易日。19 点的延期状态卡采用独立发布身份、只生成一次，发送窗口到 19:15；再晚仅保留后台及 O01 故障状态，不补刷研究群。

初期只允许广东服务器作为正式定时发布方。Windows、CI、GitHub Actions、Vercel 预览环境默认不发送；不能两台机器分别用独立数据库跑同一订阅。复用现有调度器接入队列，不再增加一套互不协调的 cron。

### 资讯扫描范围与降噪

- 默认监测“用户自选池 ∪ 最近一次有效策略候选池”；若策略池已过期要显示覆盖边界，不把旧候选说成今日全市场。额外保留市场级重大政策来源，不假定全市场公告已完整扫描。
- 先抓标题/索引和元数据，再按重要性、主体相关性抓正文；不每 15 分钟下载全部上市公司公告。使用游标、水位、重叠时间窗及供应商公告 ID 去重，允许晚到、更正和撤回事件。
- 直接发行人、交易对手、行业背景分开标注；证券代码、公司全名、发布时间和原文链接参与校验。整版报纸不能仅因提到某公司就当成其公告。
- 发布时间、采集时间和事件发生时间分别保存；查不到发布时间的材料只能作待核实背景，不能用采集时间包装成突发新闻。晚到、更正与撤回必须说明其原始事件日期。
- R02 默认每天最多 6 个即时批次，溢出合并摘要；20:30 可发一份未发事件汇总。重大事件优先占用预算，不因额度满就丢失；群内显示尚有待汇总事件。普通重复事件不发。
- S01—S10 默认每天一份，列新入选/持续入选/退出，不只重复名单。O01 同类故障冷却 30 分钟，恢复单独通知一次；正常状态不刷屏。

## 6. LLM 怎样参与

流程：`授权数据 → 日期/覆盖验收 → 硬条件筛选 → 确定性评分 → 风控 → 固化候选 → LLM解释 → 一致性校验 → 审核/发布`。

### 三种模式

| 模式 | 排名来源 | 模型职责 | 失败处理 |
| --- | --- | --- | --- |
| `off` | 规则 | 不调用 | 输出事实和规则原因 |
| `explain_only`，新订阅默认 | 规则及最终风控 | 解释入选原因、事件影响、缺口和风险；不改名单/排序 | 合格规则榜照常生成，注明 AI 解读不可用 |
| `rerank`，显式开启 | 规则初筛后有限候选 AI 重排，再执行最终风控 | 在白名单内重排并给证据 | 按明确策略回退规则排序，卡片标记；不能伪造 AI 分 |

`explain_only` 是本期拟新增契约；现有筛选流程已支持 AI 重排，不能宣称目前就已实现上述三模式。每种模式、模型与 prompt 版本均进入配置快照，旧手动流程不被暗改。最终风控后须重新校验全部叙述，不得正文仍“积极买入”而最终状态已变成风险观察。

输入仅包括：本次冻结的候选、真实指标、硬条件、最终风险状态、带 ID 的新闻/公告证据和时间。新闻正文是待分析资料，不是模型可执行指令；不给模型 Webhook、凭据、管理员信息、无关私有持仓。

输出采用结构化 Schema：总览、逐股解释、证据 ID、事实/推断标签、风险与缺失项。校验器检查股票白名单、数值一致性、引用存在、日期及风险表述；拒绝新增股票、虚构消息、无依据目标价和收益保证。模型自报 confidence 不是胜率。

默认解释 Top 5；共享单股证据缓存，但不同策略的入选逻辑不能复用成同一段无差别文案。相同策略/参数/数据批次/模型版本只生成一次，多群复用；送达重试不重新生成报告。

建议试用预算：此订阅子系统每天最多 20 次模型请求，重试也计数，单次沿用可配置超时且最多重试一次；实际 token 和费用按供应商可用账单统计，未知费用不能填零。模型 Key 共用现有配置，不自动切换额外付费厂商。预算用尽时优先保留规则榜和事实事件摘要，不阻断必要的数据采集及运维告警。这个预算不包含用户手动分析，后台必须分别展示两类用量。

## 7. 发到群里的内容与格式

### 策略日报

一份结构化 `ResearchEnvelope` 渲染为飞书卡片，不能把大段模型输出未经检查直接转发。默认包含：

1. 策略名、策略版本、交易日期、报告生成时间、状态（正式/观察/降级/延期）。
2. 股票池范围、快照/技术验证覆盖、缺失项；排序模式（规则/AI 重排）及数据来源。
3. Top N 代码与名称；各 1—2 条实际规则命中依据；关键指标与风险；区分规则分和 AI 分。
4. 新入选、持续入选、退出；只与同策略、同股票池和可比参数的上次有效报告比较，参数变更后重新建立基线。
5. 重要公告/新闻原文链接，显示发布时间、关联类型和已核实事实；附“推断”标签的解释另列。
6. 运行编号、数据截至日期与风险声明，便于复查和纠错。

格式示意（不是当前市场结果；符号仅展示字段位置）：

```text
阶跃｜放量突破 · 收盘筛选
交易日：YYYY-MM-DD   模式：规则排序 + AI解释
数据：当日收盘批次；技术验证 n/m；事件信息存在缺口

01 股票代码 · 股票名称  |  规则分 s
依据：实际量比 x；突破指标 y；对应阈值 z
风险：某项可选数据未核实；已确认风险另列
变化：新入选 / 持续入选

新增 a 只 · 退出 b 只 · 共 c 只满足规则
证据：公告标题、发布时间、原文链接
Run：可追溯编号  |  研究观察，不执行交易
```

“0 只符合条件”须有完整验收支持；失败卡片只能说“本次未能形成有效筛选结果”，并给失败原因/数据日期。公告未抓到不写“公司无风险”。

### 其他三类卡片

- ETF：完整资产池、动量排名、当前模型观察、调仓条件是否到达、防守资产、下一交易日执行假设；缺数则隐藏正式目标。收益仅来自验证过的回测口径，不把信号分称为收益预测。
- R01：市场事实 → 关键变化 → 可能影响 → 需要观察的条件；只在数据和规则可比时统计策略共振。多策略同时选中可能来自同一因子，不能称独立验证或提高胜率的证据。
- R02：事件、直接主体、发布时间、原文事实、可能影响及反例、关联候选策略；更正/撤回应明确替代哪条事件。

工程格式约束：内部卡片软预算 16 KiB（自定工程预算，不是宣称飞书平台上限）；先压缩解释再分页，保留核心事实。每片注明运行编号及 `1/N`，最多 3 片；仍超限则阻断渲染并报错，不静默漏股票。每片分别记录投递结果。

V1 卡片自包含，不放 `127.0.0.1` 链接，不向伙伴暴露管理员后台。原文链接只能指向已核验的公开来源；后续若提供完整报告页面，需独立只读授权，不默认公开报告。Webhook 卡片不承诺按钮能直接修改订阅，交互管理留到应用机器人版本。

## 8. 后端设计与边界

保留现有 FastAPI、服务层、筛选器、ETF 引擎、调度与存储边界，不另建独立通知系统。建议新增小模块承担以下职责：

| 单元 | 输入 → 输出 | 依赖与责任 |
| --- | --- | --- |
| 目标/订阅管理 | 群配置、策略 ID、参数 → 版本化订阅 | 认证、凭据引用；不执行采集 |
| 数据准备与门禁 | 日期、股票池、依赖声明 → 数据批次和质量报告 | 现有 provider/cache；逐源限流、状态清晰 |
| 订阅任务编排 | 到期订阅 + 合格批次 → 固化研究报告 | 现有策略/ETF；关闭旧自动通知 |
| 解读与格式化 | 冻结结果 + 证据 → 已校验卡片 | 现有模型配置；不自行选目标群 |
| 发布/投递队列 | 获批报告 + 明确目标 → 持久投递状态 | 单目标 sender；不回退全局广播 |
| 运维与审计 | 各阶段状态 → 后台状态和受控 O01 告警 | 不让一个失败群触发所有成功群重发 |

### 持久化契约

优先复用现有研究运行记录；新增专门的目标、订阅、任务 occurrence、outbox 和 attempt 记录，不把历史通知表硬当任务队列。建议逻辑字段：

- 目标：`destination_id / alias / type / credential_ref / credential_version / enabled`。数据库和 API 常规响应不存明文 Webhook。
- 订阅：稳定 ID、目标 ID、策略 ID/版本、参数与股票池快照、Top N、LLM 模式、时区/时点、截止时间、审核策略及配置版本。
- occurrence：`subscription_id + scheduled_for` 唯一；冻结配置、交易日、输入批次、计算状态、租约和尝试代次。不同订阅可引用同一个计算结果。
- 计算身份：策略版本、参数 hash、股票池 hash、输入批次、模型/prompt 版本与风控版本；不含目标群。一次 occurrence 首次选定合格数据批次后冻结，不能每次重试自动换快照重发。
- 发布身份：目标、订阅 occurrence、报告 revision、分片编号组成唯一键；保存批准的渲染版本及各自 payload hash、目标版本、尝试次数、下次重试时间、`not_after`、lease、平台回执等。
- 审核：批准人、时间、报告 hash、目标集合、配置版本、有效期。审核时可同时批准由同一冻结事实确定性生成的卡片与文本两个版本；各自保存 hash。未被批准的文字、规则、目标或凭据版本改变均使旧批准失效，不让历史待发报告悄悄转群。

先固化报告草稿；获批发布时在同一事务中冻结发布版本并创建 outbox。所有投递仅使用预先批准的渲染 payload，sender 不能临时改写研究内容；请求签名/时间戳是传输信息，单独记入 attempt，不改变研究正文 hash。采用原子领取、租约及尝试代次校验，防止失去租约的旧工作进程继续写入结果。

计算任务租约可以按状态恢复；发送任务必须在开始外部请求前持久记录 `sending`。其租约失效、请求后崩溃，或无法确定是否已经开始请求时，一律转 `delivery_unknown`，不能自动回到 `pending`。只有确定尚未开始发送的领取才可安全重试；晚到回执保留审计，不让旧 worker 自动启动下一分片或二次发送。

任务状态区分 `waiting_data / running / draft / ready / blocked / expired`；投递区分 `pending / sending / sent / retry_wait / rejected / delivery_unknown / suppressed / cancelled`。计算失败重算与消息失败重投是两条恢复链，不能混在一起。

### 必修的发送可靠性问题

现有 Webhook 路径把超时折叠成失败，卡片失败后会尝试文本降级；如果飞书已收卡但响应丢失，可能重复发送。因此：

1. 平台明确确认成功才记 `sent`；HTTP 200 本身不够，还要验证业务响应。成功表示平台接受，不表示群成员已读。
2. 只有明确的格式拒绝，且同一发布已预先批准文本版本时，才允许一次文本降级；任一格式已成功则不再尝试另一格式。没有获批文本时须新 revision 重新审核，不能由 sender 即时生成。认证/签名/关键词错误应停止并报 O01。
3. 明确限流拒绝按供应商反馈有界退避，发送内容不改变。网络超时、断连或进程在发请求后崩溃视为 `delivery_unknown`，Webhook 不自动重试或改发文本，由管理员确认后决定是否补发。
4. 本地 outbox 可防大部分重复领取，不能凭空保证外部恰好一次投递。应用机器人未来可使用持久 UUID，但仍要核验平台幂等期限和语义。
5. 各群、各分片独立确认；一个群失败不重发其他群。缺少目标或未知路由必须拒绝，不能退回全局通知渠道。

### 凭据、暂停与运维

- 凭据通过独立受限配置或凭据服务保存，服务器文件限制为服务账号可读（如 0600），Windows 使用对应 ACL；普通 DB 存引用。任何秘密均不进入 YAML、日志、模型或报告，异常日志须对 URL 的 token 路径脱敏。
- 管理接口要求既有身份认证及相应权限，处理跨站请求保护；秘密只写、掩码展示。Webhook 校验 HTTPS 和允许的官方目标域，禁止任意内部地址，避免配置入口成为请求内网的通道。
- 提供全局停发、单群暂停、单订阅暂停；worker 发送前再次核对开关/批准。暂停取消未发队列，不删除审计；恢复不默认补发所有历史消息。
- O01 自身失败时写本地日志/后台状态，不递归调用自身告警。启用前必须留一个可登录的后台排障入口。
- 数据任务初期共享缓存、同源有限并发；建议一个重计算任务、采集并发上限 2、模型并发 1、飞书发送串行且有间隔，随后按配额和压测调整。实际限流以供应商为准。
- 现有服务器容量巡检为 4 核、约 15 GiB 内存，可作为内部日终试用起点；不能由此推定全市场分钟级扫描已足够。先监测峰值内存、最慢策略、SQLite 锁等待和供应商限流，V1 不引入 Redis/Kafka 等额外集群。

## 9. 后台配置页面需要增加什么

融入现有框架新增“推送订阅”管理区域，不另造一套登录和导航。

1. 群目标：编号、用途、凭据状态、签名状态、最近一次投递；编辑凭据与“发测试”分离。
2. 订阅：选择策略、股票池、参数、Top N、LLM 模式、时间、是否仅变化时发送、审核方式；支持复制配置但不自动启用副本。
3. 数据就绪看板：交易日、来源、权限、覆盖率、最新业务日期、缺失原因、预计下一次补采；不用一个绿色“已配置”代表真可用。
4. 报告预览/待审箱：目标群、内容、证据、覆盖、LLM 用量、风险门禁；明确批准本次还是开启以后自动审核规则。
5. 投递记录：成功、明确失败、未知、延期及分片状态；未知补发须二次确认可能重复。

配置前后端使用同一 Schema。默认禁用，保存不发消息。策略参数/目标变更写审计，旧订阅与现有单群通知保持兼容但彼此不会自动广播。

## 10. 开发顺序与交付门槛

本 spec 经确认后再写逐文件实施计划。每阶段可独立验收，不能把建群完成视为上线完成。

| 阶段 | 开发交付 | 验收门槛 |
| --- | --- | --- |
| P0 基线 | 核对服务器冷启动、配置持久化、模板打包、认证及现有事实/风控一致性 | 服务重启后配置有效；不过度信任健康接口；关键证据链回归通过 |
| P1 配置 | 目标、订阅、凭据引用、管理 API/UI、默认禁用及预览 | 15 个目标可登记；无明文泄漏；保存不外发 |
| P2 数据 | 依赖声明、共享批次、交易日历、增量采集、覆盖门禁 | 10 策略和 ETF 明确何时能运行；缺数不冒充空结果 |
| P3 内容 | 订阅任务、冻结运行、LLM 三模式、报告契约、新闻归属及卡片 | 离线样例覆盖全部策略；不调用旧全局通知；冲突解释被挡住 |
| P4 投递 | 持久 outbox、送达未知、审核、暂停、降噪与记录 | 重启/并发/分片/限流/超时故障注入通过 |
| P5 联调 | 经用户确认向 T00 实际测试，随后验证一个完整交易日的数据链 | 费用和覆盖可见；逐群确认后启用；正式群不默认自动开通 |

回测成交价跳空处理、收益统计和样本外验证须在发布任何绩效排名前专项验收；不能仅因策略成功运行就宣传其有效收益。当前项目已有的财务/公告/风险修复须走真实历史与通知出口回归，不能只看单元函数输出。

### 必须覆盖的验收场景

- 十个策略都能绑定自己的群；改中文名不改路由；缺目标不走默认群；同一目标重复录入给出警告。
- 节假日无 A 股新榜；ETF 周内最后交易日遇节假日仍正确；T-1 价格不会标成 T 日收盘。
- 正常 0 候选、核心采集失败、可选新闻未核实分别显示；权限拒绝不无限重试；候选补数上限不会伪装全市场覆盖。
- ETF 防守资产当天缺价时阻断正式目标；复权、日期或货币单位冲突不能混算。
- LLM 编造代码/数字/引文、遗漏关键风险、与最终风控冲突会被拒绝；模型挂掉仍可形成合格规则报告。
- 多工作进程、重启、重复触发不会产生重复 outbox；丢失租约的旧进程不能提交；单群失败不会重发全部群。
- 平台 HTTP 200 但业务失败不记成功；网络超时不自动文本补发；人工补发明确提示重复风险。
- 平台已收消息、进程尚未写成功即崩溃，以及 `sending` 租约失效，都进入未知而不是自动重发；没有预先批准文本时不自动降级。
- 审核后改内容/参数/目标会失效；暂停能拦住未发任务；CI/Windows 误启不能成为第二个正式发布方。
